## 1. Протокол аудита пространства

Для каждого пространства проверяются одни и те же двенадцать измерений. Так отчёты становятся сравнимыми, а не зависят от того, на что смотрел автор.

| # | Измерение | Что фиксируется |
|---|---|---|
| 1 | **Идентичность** | Кто владеет заголовком и статусом; нет ли двойного заголовка или конкурирующих подзаголовков |
| 2 | **Иерархия** | Что главное на экране; сколько визуальных «пиков»; соответствует ли плотность характеру пространства по конституции |
| 3 | **Первый экран** | Что пользователь видит и может сделать сразу, без прокрутки и лишних кликов |
| 4 | **Состояния данных** | Покрытие загрузкой, пустотой, ошибкой, частичным отказом; есть ли честная заглушка «в разработке» |
| 5 | **Дубли** | Повторяющиеся метрики, действия и панели внутри пространства и между пространством и оболочкой |
| 6 | **Визуальная конституция** | Плотные фоны, локальное стекло, свои скроллбары, цвета и длительности вне токенов |
| 7 | **Оконный слой** | Сколько модалок, свои ли оверлеи, есть ли фокус и роли |
| 8 | **Клавиатура** | Что выполнимо без мыши; где фокус теряется |
| 9 | **Обратная связь** | Что происходит при сбое; сколько молчащих `catch` |
| 10 | **Размер и структура** | Крупнейшие файлы, дубли логики, давление на лимит 400 строк |
| 11 | **Тексты** | Инлайн-переводы, англоязычные вставки, формулировки, эмодзи в хроме |
| 12 | **Мёртвые части** | Компоненты и функции без применения |

## 2. Формат отчёта

Каждый разбор — файл в `spaces/` по шаблону:

1. **Паспорт:** размер, состав файлов, что делает пространство.
2. **Замеры:** таблица по двенадцати измерениям с числами.
3. **Дефекты:** пронумерованный список с ссылками `файл:строка` и оценкой влияния (высокое / среднее / низкое).
4. **Что сделано хорошо:** обязательно — чтобы не сломать при исправлении.
5. **Предлагаемые изменения:** по одному пункту на дефект, с указанием слоя (L0–L3 из [`../01-vision.md`](../01-vision.md)).
6. **Итерации:** 3–5 связанных файлов на итерацию, с критериями готовности.
7. **Связи:** пересечения с фронтами F1–F6 и с планом [`../04-tasks-settings.md`](../04-tasks-settings.md).

**Порядок работ:** планировалось проводить разбор **после** фронта F1 (токены и примитивы), чтобы не переписывать рекомендации. Отклонение: разбор выполнен до F1, поскольку он нужен был для полной картины. Компенсация — все предлагаемые изменения в отчётах адресованы слоям L0–L2 из [`../01-vision.md`](../01-vision.md), то есть формулируются в терминах токенов и примитивов, а не конкретных значений.

## 3. Очередь и стартовые гипотезы

Гипотезы взяты из системного прохода: это не выводы, а то, что нужно проверить при разборе. Очередь пройдена 19.09.2026 — по каждому пункту ниже есть отчёт в `spaces/`; гипотезы либо подтверждены, либо сняты.

### 3.1. Chat — первый в очереди (21 файл / 4125 строк)

Известно: второй по объёму комплекс; `MessageBubble` (372) и `ChatInputZone` (366) у лимита; в `MessageBubble` собственный лайтбокс с плотным фоном; сессии и история — в отдельном сайдбаре.
Проверить: плотность истории сессий и её роль относительно диалога; поведение при длинных сообщениях и блоках кода; состояние пустого нового диалога; отсутствие сдвигов разметки при потоковой генерации; вложения; клавиатурные сценарии чтения и копирования; не конкурирует ли композер с глобальной консолью.

### 3.2. Commands (18 / 3837)

Известно: `MacroEditorView` строит собственный модальный слой с плотным фоном; `SkillsTab` — выпадающее меню с плотным фоном; реестр команд большой.
Проверить: находимость команды (поиск, категории, недавние); понятность того, что делает команда до запуска; редактор макросов как среда (а не как форма); связка с диалогом подтверждения опасных операций; пустые состояния реестра.

### 3.3. Objectives (10 / 1647)

Известно: крупные заголовки вне типографической шкалы; `TopologySection` с собственным плотным фоном и жёстким цветом текста; откат цели через системные диалоги.
Проверить: жизненный цикл цели (черновик → активна → выполнена); читаемость карты траекторий; строка метрик (не дублирует ли она телеметрию оболочки); диагностический раздел; поведение на узкой ширине.

### 3.4. Memory (7 / 1255)

Известно: ошибки импорта JSON через системное окно; подтверждение очистки — свой оверлей с плотным фоном и высоким слоем.
Проверить: типы узлов и их различие; поиск и фильтры; импорт/экспорт; модалка деталей; связи между узлами; пустое состояние; явность локальности хранения (важно для доверия).

### 3.5. Core и shell (оболочка)

Известно: `TitleBar` (380) у лимита; слой виджетов с произвольным слоем; панель голоса с плотным фоном; `SpotlightSearch` с плотным фоном; терминальная консоль с плотным фоном; `FpsOverlay` (963, легаси) — самый большой файл проекта.
Проверить: эргономику перетаскивания и прилипания виджетов; различие режимов «Чистый центр» и «Свободный»; плотность телеметрии в верхней полосе; ценность терминальной консоли для пользователя; роль палитры команд как основной навигации (идея из видения, пункт 4).

### 3.6. Transcription (2 / 1393)

Известно: всё пространство в одном файле на 552 строки.
Проверить: выбор устройства и модели; прогресс загрузки; список результатов; экспорт; состояния ошибок и пустоты; структурный долг (один файл на пространство).

### 3.7. Малые пространства: Files, Vision, Modules, modelDownload (4 файла / 1047 строк)

Проверить: соответствие контракту пространства (заголовок, состояния, клавиатура, стекло); не выглядят ли они «модулями в разработке»; общий ли язык с остальными.
