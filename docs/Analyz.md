## 2.1. P0 — CI падает из-за CacheService

<badge>Критический приоритет</badge>

Подтверждённая проблема:

`src/main/ipc/ai.ipc.test.ts`

Ошибка:

`EACCES: permission denied, mkdir '/mock/app/userdata/audio-cache'`

Стек указывает на:

- `src/main/services/cache.service.ts:33`
- `src/main/services/cache.service.ts:229`
- `src/main/services/tts.service.ts:9`

Причина по текущей реализации:

В `cache.service.ts` создаётся экземпляр:

`export const cacheService = new CacheService();`

Конструктор немедленно пытается создать папку кэша через `fs.mkdirSync`.

Путь определяется через `app.getPath('userData')`, а если Electron API недоступен — через временный системный каталог.

В результате импорт сервиса может вызывать побочные операции с файловой системой ещё до того, как основной код действительно использует кэш.

В тестовой среде Electron возвращает фиктивный путь `/mock/app/userdata`, где запись запрещена.

Это не просто проблема теста. Текущая архитектура означает, что недоступность необязательного файлового кэша потенциально способна сорвать импорт TTS или другого зависящего от него сервиса.

**Что необходимо сделать:**

1. Убрать файловые побочные эффекты из момента импорта модуля.
2. Пересмотреть момент инициализации CacheService.
3. Рассмотреть ленивую инициализацию при первом реальном обращении.
4. Предусмотреть передачу пути кэша через конструктор или конфигурацию, чтобы тесты могли использовать временные каталоги.
5. Сделать CacheService устойчивым к ошибкам файловой системы.
6. Если кэш недоступен, приложение должно продолжать работу без кэширования, а не падать.
7. Ошибки кэша должны логироваться корректно, без бесконечного повторения одних и тех же сообщений.
8. Обеспечить корректное восстановление после восстановления доступа к каталогу, если это предусмотрено архитектурой.
9. Не использовать в производственном коде жёстко заданный тестовый путь `/mock/...`.
10. Не ограничиваться изменением теста ради зелёного CI: устранить архитектурную причину.

**Обязательные тесты:**

- Импорт `cache.service.ts` не создаёт файлы и каталоги.
- CacheService работает с корректным временным каталогом.
- CacheService не ломает приложение при недоступном каталоге.
- Ошибка создания директории не приводит к отказу TTS.
- Ошибка записи индекса не приводит к аварийному завершению приложения.
- После восстановления доступности каталог снова может использоваться.
- Повторная инициализация не создаёт повреждённое состояние.

## 2.2. P0 — Проверить безопасность файлового индекса CacheService

В текущем `cache.service.ts` индекс читается из `index.json` через `JSON.parse`, после чего используется без полноценной проверки каждой записи.

Особое внимание:

- `loadIndex()`
- `get()`
- `put()`
- `enforceLimits()`
- `evict()`

В `evict()` выполняется удаление файла по `entry.path`.

Проверь риск, при котором повреждённый или подменённый индекс содержит путь за пределами каталога `audio-cache`, после чего очистка кэша может обратиться к постороннему файлу.

**Требования:**

1. Проверять структуру каждой записи индекса.
2. Проверять типы `path`, `hitCount`, `lastAccessMs`, `sizeBytes`, `isSpeedTier`.
3. Нормализовать пути через `path.resolve`.
4. Проверять, что путь действительно находится внутри разрешённого каталога кэша.
5. Запрещать удаление любых файлов вне каталога кэша.
6. Некорректные записи удалять из индекса, не затрагивая посторонние файлы.
7. Не доверять содержимому JSON только потому, что он находится в `userData`.
8. Добавить тест на подмену пути в индексе с попыткой удаления внешнего файла.

Это обязательная проверка безопасности локального файлового кэша.

## 2.3. P1 — Неограниченный рост Speed Tier Cache

В текущей реализации:

`isSpeedTier(normalizedText)` возвращает `true` не только для фиксированных быстрых фраз, но и для любого текста короче 40 символов.

При этом записи Speed Tier исключаются из обычной очистки:

- TTL не применяется.
- При превышении лимита дискового пространства они пропускаются.
- При превышении лимита количества записей они также исключаются из удаления.

Потенциальное следствие: произвольные короткие фразы могут постоянно попадать в защищённый от очистки сегмент кэша.

**Необходимо:**

1. Проверить, действительно ли текущая политика соответствует первоначальной цели Speed Tier.
2. Не считать любой короткий текст быстрой системной фразой.
3. Использовать контролируемый список наиболее часто используемых системных реплик либо другой обоснованный механизм классификации.
4. Установить абсолютный лимит общего размера кэша.
5. Предусмотреть отдельный небольшой резерв для действительно критичных быстрых реплик.
6. Даже защищённый сегмент не должен нарушать абсолютный предел хранения.
7. Проверить корректность LRU/LFU-эвикции.
8. Не удалять часто используемые записи без необходимости.
9. Проверить, что TTL не приводит к удалению используемого аудиофайла во время воспроизведения.

Добавить тесты на массовую вставку тысяч коротких фраз.

## 2.4. P1 — Недостоверная статистика CacheService

## 5.3. Graceful Degradation

При отсутствии необязательного компонента A.R.C. должна продолжать работать в доступном режиме.

Например:

- Silero недоступен → использовать следующий доступный TTS-провайдер.
- Python недоступен → не блокировать всё приложение.
- Модель STT отсутствует → корректно отобразить недоступность соответствующего сценария.
- Облачный провайдер не отвечает → корректно показать ошибку и доступные альтернативы.
- Нет API-ключа → не выполнять бесконечные запросы и не показывать ложный статус подключения.
- Нет доступа к кэшу → работать без кэширования.

Нельзя сообщать пользователю, что функция работает, если она не работает.

Статусы должны различать:

- Active;
- Available;
- Unavailable;
- Initializing;
- Failed;
- Fallback;
- Unsupported;
- Planned.

Не использовать `Active` для незапущенных или несуществующих сервисов.

Убедись, что:

- повреждение SQLite не приводит к безусловному удалению исходной базы;
- `SQLITE_BUSY` не трактуется как повреждение;

- карантинные копии сохраняются до проверки;

- пользователь получает понятное сообщение о проблемах с данными.

Проверь, что связанные изменения сохраняются атомарно.

- массовые операции;
- импорт памяти;
- изменение нескольких связанных записей;
- миграции;
- операции, где несколько таблиц образуют единое логическое состояние.

В актуальной документации отмечался долг по `MemoryView` / `memory.store`: импорт мог выполнять последовательное сохранение элементов без общей транзакции и оставлять частично импортированные данные при ошибке.

Перепроверь этот участок.

Если проблема существует, реализуй безопасную транзакционную обработку с предварительной валидацией всего набора данных.

Не меняй существующие контракты без необходимости.

## 6.3. Импорт и экспорт

Проверь:

- валидацию входного JSON;

- обязательные поля;
- неизвестные поля;

# 12. ПРОВЕРКА SOAK TEST И ДОСТОВЕРНОСТИ СТАТИСТИКИ

Это важный пункт: существующую статистику нельзя принимать без проверки методологии.

В текущем `scripts/soak-test.js` обнаружены признаки моделирования, а не полноценного интеграционного тестирования:

- симуляция аудиоданных;
- предполагаемые значения RSS Renderer;
- предполагаемые значения RSS Python.

В частности, значения Renderer и Python RSS рассчитываются формулами, а не измеряются по реальным процессам.

При этом `docs/STATISTICS.md` описывает результаты как фактическую статистику многочасового тестирования системы.

Это методологическая проблема.

## Что необходимо сделать

Разделить тестирование на два типа.

**A. Simulation / Benchmark**

Оставить быстрые синтетические тесты для:

- алгоритмов;
- сериализации;
- математических операций;
- проверки нагрузки отдельных функций;
- проверки сценариев ошибок.

Но прямо обозначить, что результаты моделируемые.

**B. Real Integration / Soak Test**

Предусмотреть реальную проверку запущенной системы:

- реальный Electron Main;
- реальный Renderer;
- реальная SQLite;
- реальные процессы, если они запущены;
- фактическое потребление памяти;
- фактические ошибки;
- реальные таймауты;
- реальные длительные циклы.

Если TTS или LLM недоступны, тест должен явно указывать, что соответствующий компонент пропущен.

Нельзя записывать оценочные числа в поля фактических измерений.

## Проверить

- реальный RSS каждого процесса;
- общий расход RAM;
- рост памяти по времени;
- открытые дескрипторы;
- незавершённые процессы;
- количество необработанных исключений;
- повторяющиеся ошибки;
- стабильность БД;
- состояние аудио;
- корректность остановки.

Обнови `docs/STATISTICS.md`, чтобы документ не выдавал синтетическую статистику за реальные измерения.

Если существующие результаты не подтверждены реальным измерением, обозначь их как historical simulation или simulated benchmark.

Не удаляй исторические данные: сохрани их происхождение и правильную классификацию.
