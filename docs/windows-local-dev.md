# Справочник для локальной Windows-разработки A.R.C.

> **ВАЖНОЕ ПРИМЕЧАНИЕ:**  
> Это справочник только для локальной Windows-разработки A.R.C.  
> Не является инструкцией для AI Studio Agent и не должен интерпретироваться как обязательный workflow агента.

Справочный файл конфигурации и окружения для локальной разработки под Windows.

## Процесс работы (Intake -> Context -> Plan -> Execute -> Verify -> Document -> Memory -> Report)

1. **Intake**: Анализ намерений пользователя.
2. **Context**: Сбор только необходимого контекста.
3. **Plan**: Описание плана изменений.
4. **Execute**: Точечное и аккуратное внесение изменений.
5. **Verify**: Проверка изменений (lint, build).
6. **Document**: Обновление технической документации в `docs/`.
7. **Memory**: Обновление текущего состояния.
8. **Report**: Формирование структурированного ответа (Сделано, Измененные файлы, Обновленная документация, Проверки, Риски, Следующий шаг).

## Архитектура и Структура файлов
- **Модульность (Правило 400 строк):** Агенты и разработчики должны держать размер файлов логики (Vue-компоненты, сервисы, composables, утилиты) строго **в пределах 400 строк**. Файлы данных (registry, stores, config) — **до 800 строк**. 
- При создании новых фич необходимо сразу применять модульный подход (разделять UI, логику, registry, utils).
- **Механизм контроля:** Проверка встроена в процесс сборки (`npm run build`). Скрипт `npm run check-sizes` автоматически завершает билд ошибкой (`exit code 1`), если лимиты превышены.
- **Вынос логики:** Сложную UI логику следует выносить в отдельные `.ts` файлы (утилиты или composables).
- **Зона «НЕ ТРОГАТЬ» (КРИТИЧЕСКИЙ ЗАПРЕТ)**: 
  - Весь стек **3D Reactor**: `ReactorCore.vue`, `useReactor3D.ts`, `reactor-geometry*`, `reactor-materials*`, `reactor-lighting*`, `reactor-particles*`, `reactor-postfx*`, `reactor-state-driver*`, а также логика сцены/рендеринга Three.js. Текущий визуальный 3D Reactor A.R.C. является **эталонным и неприкосновенным**.
  - Запрещено создавать 2D/SVG/процедурные заглушки или менять код Reactor для "исправления" WebGL, GPU, sandbox, iframe или browser-runtime ошибок. Ошибки отсутствия WebGL в preview-окружении относятся к среде запуска, а не к приложению.
  - Файлы `useVoice.ts`, `built-in-llm.service.ts`, `useMacroEditor.ts`, `ObjectiveEngine.ts`, `BottomBar.vue`, VoiceFSM и сторы (Pinia stores) запрещено изменять без прямого отдельного разрешения.
  - **Scope Lock (Chat & Tasks)**: пространства `Chat` и `Tasks` закрыты от изменений и рефакторинга по умолчанию. Изменения разрешены только при прямом запросе пользователя на доработку этих пространств.

## State Management (Pinia & Composables)
- **Pinia**: Использовать строго для **общего состояния** (global state), доступного в разных частях приложения.
- **Composables**: Использовать для **локального состояния** (local state) или инкапсуляции специфической бизнес-логики UI.
- **ЗАПРЕТ**: Дублирование одних и тех же данных в нескольких сторах.
- **ЗАПРЕТ**: Деструктурировать реактивные поля Pinia store в `<script setup>` без `storeToRefs()`. Прямой доступ к store в `<template>` допустим.

## Правила IPC (Inter-Process Communication)
- Все обработчики IPC должны располагаться строго в файлах `src/main/ipc/*.ipc.ts`.
- Хэндлеры должны быть тонкими (Thin Handlers) — они лишь принимают запрос и вызывают соответствующий сервис из `src/main/services/`.
- Для каждого **нового IPC-метода** обязательно должно быть реализовано заглушечное поведение (Mock) в `src/renderer/bootstrap/mock-database.ts` (или аналогичных mock-файлах) для обеспечения работы web-preview.

## Запуск проекта
- **Инициализация и скачивание зависимостей/моделей:** `npm run install-scripts approve`
- **Запуск приложения (Electron) с логами:** Используйте `arc.bat` (скрывает вывод из консоли и пишет всё в файл с временной меткой в папку `logs/`).
- **Просмотр логов:** Запустите `open_latest_log.bat` (в корневой папке) для открытия последнего лога в блокноте.
- *Примечание:* Логи НЕ коммитятся в git (`logs/*.log` добавлено в `.gitignore`). Python-сервер (Silero TTS) теперь запускается и мониторится **автоматически**.

## Известные проблемы
- **Утечка памяти**: Запланирован фикс с использованием `WeakRef` для тяжелых объектов.
- **Barge-in & Голосовой тракт**: Внедрен VoiceFSM с явным `voiceMode` (`WAKE_WORD_ONLY` | `ACTIVE_DIALOGUE`), сторожевой guard `canOpenDialogueWindow()`, сброс буфера `reset_buffer` при переходе TTS → MIC, 1000ms debounce stop-word, gratitude closer перед фантом-фильтром, AudioContext guard (`safeCloseAudioContext`), VAD-гейт 15s таймера, позиционный фильтр wake-word (строго первые 3 слова + фильтр отрицаний) и вежливый голосовой ответ без зависаний.
- **STT Worker Lifecycle**: Внедрены pre-kill graceful fallback через `reset_buffer`, таймаут heartbeat 15s, circuit breaker guard и сигналы готовности `worker-ready`/`init_result`.

## Самоконтроль
- Агент должен регулярно проверять соответствие архитектуре и актуальность файлов документации.
- **Гигиена карантина LLM провайдеров**: Ошибки 400 и 404 являются ошибками конкретного запроса или удалённой модели и КАТЕГОРИЧЕСКИ НЕ ДОЛЖНЫ приводить к 10-минутному карантину провайдера в `provider-health.ts`. При сохранении настроек или успешном тесте соединения карантин и кулдаун сбрасываются немедленно.

## Принцип партии «Ревизия меню» (от 30.08.2026)
- **Отсутствие фейковых данных**: В пользовательском интерфейсе не бывает фейковых данных. Либо реальные данные, либо честная заглушка "функция в разработке" или "модуль в разработке".
- **Единый реестр имён вкладок**: Tab-меню и навигация используют `TAB_REGISTRY` в `ui.ts` для маппинга системных `TabName` (напр., `commands`, `transcription`) в визуальные лейблы (напр., «КОМАНДЫ», «АУДИО»).


## UI Theme Guidelines (Arc Glassmorphism)
- **Конституционный принцип стекла (ТЗ v3.1)**: «Стекло живёт над статикой и на кромках; мат живёт над анимацией и под текстом». Любая будущая правка стекла сверяется с ней.
- **Истинное Стекло (Glassmorphism & Depth)**: Модальные окна, панели и карточки обязаны быть полупрозрачными и парящими (`bg-[#070709]/65`, `bg-black/40`, `bg-black/50` в комбинации с глубоким размытием `backdrop-blur-2xl` / `backdrop-blur-xl`). Глухой сплошной черный фон (`bg-black/85`, `#0E0F12`) для модальных окон КАТЕГОРИЧЕСКИ ЗАПРЕЩЕН, так как превращает интерфейс в плоскую "черную дыру" и скрывает реактор и космический фон.
- **Бэкдроп (Легкая вуаль)**: Фон затемнения под модалками должен быть легкой дымкой (`bg-black/30 backdrop-blur-sm`), не размывающей задний план в монолитную кашу, сохраняя визуальную глубину сцены и реактора.
- **Мягкая Геометрия (Pill-shapes & Rounded)**: 
  - Поля ввода (Inputs) и кнопки действий должны использовать форму капсулы (`rounded-full`).
  - Интерактивные карточки и элементы списков (как в истории диалогов) должны иметь мягкие скругления (`rounded-2xl`, `rounded-3xl`).
- **Границы и Разделители**: Никаких толстых рамок. Границы должны быть едва заметными (`border-white/5`, `border-transparent`). Активный элемент в списке выделяется фоном (`bg-white/[0.05]`), а не границей.
- **Типографика**: 
  - Основной UI (названия карточек, текст кнопок, элементы управления): Чистый, читаемый рубленый шрифт (Sans-serif), нормальный регистр.
  - Мелкие подписи, категории, статусы (Badges, Tabs): Моноширинный шрифт (`font-mono`), мелкий размер (`text-[10px]`), верхний регистр (`uppercase`) и разрядка (`tracking-widest`).
- **Слои и Воздух**: Интерфейс должен "дышать". Много пустого пространства (padding). Элементы списков по умолчанию прозрачные (`bg-transparent`), фон появляется только при наведении (Hover) или выборе.

## Работа с Python-кодом (silero_server.py)
- **ЗАПРЕТ ПАТЧ-СКРИПТОВ**: `silero_server.py` изменяется ТОЛЬКО правкой файла целиком. После правки обязательны: `python -m py_compile` + реальный старт сервера + маркеры `[SILERO SERVER BUILD]`, `[DictLoader]`, `[DSP v2] selftest OK` в отчёте. Патч-скрипты (`patch_*.py`) запрещены.

## Логирование ошибок
- **ЗАПРЕТ**: Никогда не печатать полные объекты ошибок в консоль (например, `console.error(err)` для Axios/HTTP запросов), так как это может привести к блокировке main-процесса из-за переполнения stdout. 
- Только `message` / `code` (например: `console.error(\`Ошибка: ${err.code} ${err.message}\`)`).

## Архитектура STT «STT Never Dead»
- **Изоляция нативных крашей**: Нативный `exit(-1)` в sherpa-onnx/ONNX Runtime не перехватывается JS try/catch. Любая новая модель проверяется только через sacrificial-процесс (`sherpa-validator.util.ts`).
- **Circuit Breaker**: При 2 последовательных крашах воркера источник помечается как `incompatible: true` в `download_meta.json` и отключается от дальнейших попыток загрузки.
- **Старт первым**: `stt_worker.js` всегда первым стартует быстрый проверенный Whisper Small int8, гарантируя готовность голосового ввода через 1 секунду. GigaAM подключается асинхронно через hot-swap сообщение `load_gigaam`.
- **Зеркала HF**: При коде 401 или сбое соединения загрузчик автоматически переключается на зеркало `hf-mirror.com`.

## Стандарты UX/UI и Пространственной Эргономики (Директива 2026)
- **Иерархия центрального реактора**: 3D-реактор — смысловое ядро и живой аватар системы. Он не должен перекрываться хаотично висящими виджетами.
- **Принцип рабочей области (Workspace vs Modal)**: Рабочие вкладки (Чат, Задачи, Память, Команды) должны ощущаться как единая цельная рабочая среда, а не временное всплывающее модальное окно.
- **Интеграция телеметрии**: Системная информация (CPU, RAM, модель, готовность) концентрируется в статусных консолях (TitleBar / Верхняя полоса), избавляя экран от разрозненных плашек.
- **Отказ от псевдо-декораций**: Никаких случайных шестнадцатеричных счетчиков (`0x0000`) или бутафорских надписей без реальных данных. Профессионализм выражается в точности, функциональности и балансе негативного пространства.
- **Роли агентов**: Каждая доработка интерфейса валидируется через 5 ролей: **Planner** (планирование архитектуры), **Critic** (поиск узких мест и дискомфорта UX), **Auditor** (проверка целостности и правил), **Writer** (чистая реализация), **Reviewer** (самоконтроль и верификация).

## Архитектура хранилища (Portable Data Architecture)
- **Изоляция в папке приложения**: Все пользовательские данные, профили, кэши, база SQLite и модели нейросетей хранятся строго в локальном каталоге `data/` в папке программы (`app.setPath('userData', dataDir)` инициализируется до загрузки сервисов).
- **Сброс системы**: Выполняется через `StorageManagerService.resetSystemData()`. При сбросе дескриптор базы данных закрывается через `DatabaseService.close()`, очищаются файлы `data/` и легаси-профили в `%APPDATA%/a.r.c`, после чего вызывается `app.relaunch()`.

## A.R.C. Visual Constitution (Неприкосновенная визуальная философия)
- **Не SaaS и не Generic AI**: A.R.C. — живая вычислительная AI-среда, а не плоский дашборд, не Notion, не ChatGPT и не монохромная админка.
- **Основа визуальной ДНК**: Глубокий черный космос (`#000000`), живой 3D-Реактор по центру, сдержанный фирменный красный A.R.C. RED, темное стекло (`backdrop-blur-xl/2xl`), тонкие структурные линии, точная sci-fi/HUD эстетика и многослойная глубина.
- **Цветовая модель A.R.C. RED**:
  - `Identity`: Фирменное присутствие системы и акцентные маркеры.
  - `Active`: Выбранный активный экран / рабочее пространство.
  - `Focus`: Интерактивный фокус ввода / подсветка наведения.
  - `Voice`: Канал прослушивания (Listening) микрофона.
  - `Reactor`: Внутреннее свечение и реакция ядра на диалог.
  - `Critical`: Реальные системные ошибки и алерты.
  - `Ambient`: Едва заметное атмосферное свечение.
- **Разделение слоев Human & Machine**:
  - `Human Layer`: Читаемый гротеск (`Inter`), нормальный регистр, комфортный интервал для сообщений, задач, описаний и подсказок.
  - `Machine Layer`: Моноширинный (`JetBrains Mono`), разрядка трекинга, верхний регистр только для технических метаданных, таймингов, ID, телеметрии и CPU/RAM.
- **Дифференциация пространств по характеру и плотности**:
  - `CORE`: Атмосферный (доминирует Реактор, виджеты спокойны).
  - `CHAT`: Спокойный (диалог на первом месте, телеметрия по требованию).
  - `TASKS`: Структурированный (actionable-first, списки, канбан, матрица).
  - `OBJECTIVES`: Стратегический (цели, вехи, топология).
  - `FILES`: Утилитарный (навигация, превью, быстрый доступ).
  - `MEMORY`: Архивный (структурированные знания и контекст).
  - `COMMANDS`: Технический (каталог действий, макросы, шорткаты).
  - `AUDIO` & `VISION`: Мультимедийный и диагностический.
  - `MODULES`: Системная карта (статусы подсистем).
  - `SETTINGS`: Инженерный (плоская структура Секция → Группа → Строка параметра).
- **Неприкосновенность Реактора и Command Center**:
  - Поведение и масштаб 3D-Реактора неприкосновенны. Запрещено уменьшать Реактор или заменять его плоскими карточками.
  - Концепция `BottomBar` и `CommandCenter` (физический канал связи с Реактором) сохраняется; разрешена только калибровка геометрии, отступов и обратной связи.

## Master UX/UI Implementation Protocol (Строгий протокол реализации)
1. **Никакой одновременной правки множества пространств**: Работа ведется строго экран за экраном.
2. **Лимит итерации**: Максимум 3–5 связанных файлов за итерацию.
3. **Сначала макет/спецификация, затем код**: Перед внесением изменений формулируется текстовая структура слоя (Layout Specification).
4. **Контрольный тест идентичности (A.R.C. Identity Check)** по завершении каждого шага:
   - Стал ли интерфейс удобнее?
   - Стал ли он визуально спокойнее?
   - Сохранился ли характер A.R.C.?
   - Стал ли интерфейс более похож на A.R.C. или на обычный SaaS? *(Если ответ «Обычный SaaS» — немедленный откат визуального решения).*
5. **Принцип целесообразности UX (Запрет изменений ради изменений)**:
   - *Do not redesign a component merely because it can be redesigned. Every change must solve an identified UX problem.*
   - Не изменяй компонент ради визуального обновления. Каждое изменение должно решать конкретную выявленную UX-проблему. Если существующее решение уже работает и соответствует визуальной конституции A.R.C., оставь его без изменений.
